# مشاريع القنوات وتنفيذ الوكلاء الموثوق

المراجعة الأساسية للمصدر (Buzz 0.5.23):

`4ab4f786085a23fe6126529861840eff6048ceee`

هذه الوثيقة تصف ما هو **منفّذ ومختبر** في هذه النسخة من Buzz، وحدوده الفعلية. كل ادعاء فيها مربوط بمصدر أو باختبار. الأجزاء غير المنفّذة مذكورة صراحةً في القسم الأخير.

## الفكرة في سطر واحد

المشروع ينتمي إلى **القناة** على هذا الجهاز فقط: يُربط مجلد محلي بقناة، يُختار فريق من الوكلاء الموجودين ومنسق، تُفحص جاهزيتهم الفعلية، تُعطى مهمة واحدة محدودة، ثم يُتابع التسليم والمراجعة المستقلة والقبول من لوحة مهام لا يتقدّمها إلا سجل موثق.

المسار المحلي للمجلد لا يُنشر إلى المجتمع أبداً؛ يبقى في قاعدة البيانات المحلية للتطبيق.

## الدليل السريع

١. أنشئ قناة، واختر في نموذج الإنشاء:
   محادثة فقط، أو إلحاق مجلد موجود عبر منتقي المجلدات الأصلي، أو إنشاء مشروع جديد داخل مجلد تختاره (لا يُستبدل أي ملف موجود).
   لقناة قائمة: افتح زر
   `Project`
   في رأس القناة، ثم تبويب
   `Workspace`
   واختر المجلد.

٢. في تبويب
   `Team and permissions`
   اختر المنسق من الوكلاء الموجودين، وأضف الأعضاء، وحدد لكل عضو دوره وصلاحياته، وأضف أوامر الفحص المعتمدة، ثم احفظ.

٣. راجع قسم
   `Readiness`
   تحت الفريق: يعرض سلّم الحالات وكل فحص مع سبب الفشل وخطوة الإصلاح ووقت آخر فحص. شغّل
   `Run isolated local inspection`
   لإثبات مجلد العمل الفعلي والفرع والمراجعة وحالة التغييرات غير الملتزمة.

٤. إن كان المشروع موروثاً من جلسة سابقة: افتح تبويب
   `Review`
   ثم
   `Inspect handoff`
   لقراءة ملف التسليم وحالة git الحية والعمليات الأخرى داخل المجلد، وأكد صراحةً تحرير الكاتب السابق. أو استورد ملخصاً مكتوباً.

٥. في تبويب
   `Tasks`
   خطّط مهمة واحدة محدودة وأسندها للمنسق. الإسناد ممنوع ما لم تكن الحالة
   `execution_authorized`

٦. تابع الحالة: المنفّذ يبدأ ويسلّم بمراجع مخرجات، المراجع المستقل يقرر، ثم يظهر لك زر القبول. التقرير النهائي للمنسق يُعرض بالعربية وبمصطلحات إنجليزية على أسطر مستقلة.

٧. راجع التغييرات في تبويب
   `Review`
   ثم
   `Review changes`
   قبل القبول. Buzz لا يلتزم ولا يدمج ولا يدفع ولا ينشر نيابة عنك.

٨. للإيقاف: زر
   `Pause project work`
   يوقف الإسناد والبدء الجديد ويجعل كل نداء أداة يرفض عمل المشروع عند فحصه التالي، دون قتل العمليات ودون حذف أي عمل. الاستئناف بالزر نفسه.

## سلّم الجاهزية

| الحالة | معناها |
|---|---|
| `conversation_only` | لا مشروع مرتبط بالقناة |
| `selected` | ربط محفوظ لكن المجلد غير متاح على هذا الجهاز |
| `attached` | المجلد صالح؛ الفريق أو المشغّلات أو السجلات ما زالت غير مهيأة (توجد فحوص فاشلة) |
| `runtime_configured` | كل عضو على مشغّل بإنفاذ محقق، أُطلق بسلطة المشروع الحالية، ولا عوائق |
| `access_verified` | الفحص المعزول أثبت مجلد العمل الفعلي لهذا الربط وهذا الفريق |
| `execution_authorized` | كل ما سبق وغير موقوف |
| `task_running` | توجد مهمة في حالة التشغيل |

كل تغيير في الربط أو الفريق يُبطل نتائج الفحص السابقة (تُخزَّن مع جيل الربط وجيل الفريق).

## مصفوفة دعم المشغّلات

المصدر الوحيد لهذه الحقائق هو كتالوج المشغّلات في المصدر:

`desktop/src-tauri/src/managed_agents/discovery/catalog.rs`

| المشغّل | مستوى الإنفاذ | الكتابة | القراءة | الأوامر | الشبكة | الدليل |
|---|---|---|---|---|---|---|
| Buzz Agent (`buzz-agent`) | أدوات أصلية معزولة بـ sandbox-exec | مقيدة للمشروع | مقيدة للمشروع | لا أوامر عامة | ممنوعة | اختبارات تكامل بنموذج اصطناعي (`crates/buzz-agent/tests/project_workspace.rs`) |
| Claude Code (`claude-agent-acp` 0.77) | بوابة أذونات في `buzz-acp` بوضع `default` | مقيدة عبر البوابة | **غير مقيدة** (Claude Code لا يطلب إذناً للقراءة) | قائمة الفحوص المعتمدة عبر البوابة | غير ممنوعة | `crates/buzz-acp/src/project_gate.rs` واختبارات `pool::project_gate_tests` |
| Codex (`codex-acp` 1.11) | وضع `read-only` = صندوق رمل `workspace-write` الخاص بـ Codex | مقيدة للمشروع بواسطة نظام التشغيل | غير مقيدة | تعمل داخل الصندوق دون موافقة لكل أمر؛ التصعيدات تمر بالبوابة | ممنوعة | إعلان الكتالوج + قراءة شيفرة المحوّل المثبت |
| Goose | **غير مدعوم** للمشاريع (وضع `auto` بلا طلبات أذونات) | – | – | – | – | إعلان الكتالوج |
| المشغّلات المخصصة والبعيدة والمسبقة | **غير مدعومة** للمشاريع | – | – | – | – | يُرفض التشغيل للعضو فقط، ولا يُستبدل المشغّل |

قاعدتان مهمتان:

- البوابة ليست صندوق رمل. ما تستطيع منعه هو فقط ما يمرره المشغّل عبر
  `session/request_permission`
  والكتالوج يعلن لكل مشغّل ما الذي يشمله ذلك.
- عضو على Codex بلا صلاحية `edit` أو `run_checks` لا يحصل على جلسة مشروع أصلاً (لأن صندوق Codex لا يستطيع منع الكتابة لكل تعديل ولا حصر الأوامر بقائمة)؛ يظهر ذلك كفحص فاشل مع الإصلاح المقترح.

الوكلاء الذين ليسوا أعضاء في فريق مشروع يعملون كما كانوا: محادثة فقط، بلا سياق مشروع، **ولا يقيّدهم المشروع**.

## الصلاحيات

الأدوار (تسمية للمسؤولية):
`coordinator`, `manager`, `writer`, `tester`, `reviewer`, `member`

الصلاحيات (الشيء الوحيد الذي يُنفَّذ):

| الصلاحية | أثرها الفعلي |
|---|---|
| `read` | قراءة داخل المشروع |
| `edit` | تعديل داخل المشروع (ما عدا `.git` ومخازن الأسرار) |
| `run_checks` | تشغيل أوامر مطابقة نصياً لقائمة الفحوص المعتمدة |
| `manage_team` | تعديل قائمة الفريق ضمن صلاحيات المنسق نفسه فقط |
| `assign_tasks` | تخطيط المهام وإسنادها وتقديم التقرير النهائي |
| `review` | مراجعة تسليم لم يعمل عليه (المنفّذ لا يراجع نفسه) |
| `create_private_channels` | أوامر `buzz channels create/add-member/invite` |
| `commit_merge` | `git add/commit/merge/checkout` محلياً، **بلا** `push` |

النشر والدفع والنشر السحابي والشراء والحذف التدميري غير قابلة للمنح؛ كل طلب يُرفض ويُسجَّل في طابور الموافقات لقرارك لكل حالة.

## طابور الموافقات

أي طلب رفضته البوابة ويمكن لإنسان الموافقة عليه يظهر في تبويب
`Approvals`
مع الفئة والأمر أو المسارات والسبب ووقت الطلب. الموافقة على أمر مع خيار "إضافته إلى الفحوص المعتمدة" تُنشئ جيل فريق جديداً، فتعيد الجلسات الجارية حساب صلاحياتها في الدور التالي. الموافقة لا تنفّذ شيئاً بنفسها.

## لوحة المهام

الحالات:
`planned`, `waiting_input`, `assigned`, `running`, `delivered`, `under_review`, `blocked`, `awaiting_owner_approval`, `completed`, `paused`, `cancelled`

القواعد المنفَّذة في آلة الانتقالات المشتركة
(`crates/buzz-agent/src/project_workspace/tasks.rs`):

- الإسناد مرفوض لمهمة لها منفّذ نشط، أو لها اعتماديات غير مكتملة، أو مدخلات ناقصة، أو أثناء الإيقاف.
- التسليم يُسجَّل مرة واحدة ويتطلب مرجع مخرجات واحداً على الأقل.
- المراجعة مستقلة: المنفّذ لا يراجع تسليمه.
- القبول من المالك فقط وبعد مراجعة معتمدة؛ التقرير النهائي لا يُقدَّم قبل ذلك.
- كل انتقال مفصول بجيل المهمة وجيل الربط؛ تغيير المجلد لا يعيد توجيه مهمة قائمة.

الإشعارات: كل انتقال يحتاج إيقاظ وكيل يسجّل نية إرسال؛ يرسلها التطبيق كرسالة عادية في القناة تحمل علامة
`buzz-project-task:<id>:<revision>`
فإذا انقطع الإرسال بعد النشر وقبل تسجيل الإيصال تُعرض الحالة "غير مؤكدة" ويُصالَح ذلك بالبحث عن العلامة على الخادم قبل أي إعادة، بحد ثلاث محاولات ثم القرار لك. لا يوجد ادعاء تنفيذ مرة واحدة بالضبط.

أدوات الوكلاء:
`project__task_list`, `project__task_get`, `project__task_start`, `project__task_deliver`, `project__task_block`, `project__task_request_input`
وللمنسق:
`project__task_create`, `project__task_assign`, `project__task_provide_input`, `project__task_report`
وللمراجع:
`project__task_review`

تُقدَّم للوكلاء الأصليين مباشرة، ولمشغّلات Claude/Codex عبر خادم MCP محلي
`buzz-agent --project-task-mcp`
يُسجَّل تلقائياً في جلسات المشروع.

## الترحيل والاستعادة

جداول جديدة في قاعدة البيانات المحلية، كل منها بترحيل ذري مسجّل في
`archive_migrations`:

`project_approval_requests_v1`, `channel_project_tasks_v1`, `channel_project_inspections_v1`, `channel_project_handoffs_v1`

الحقول الجديدة في لقطة الفريق (`approved_checks`، الأدوار والصلاحيات الموسعة) متوافقة رجعياً: اللقطات القديمة تُقرأ بقيم فارغة. إعادة تشغيل التطبيق تستعيد الربط والفريق والمهام والموافقات ونيات الإرسال؛ النية التي بدأت ولم تُؤكَّد تصبح "غير مؤكدة" وتنتظر التسوية.

## التحقق

الأوامر المستخدمة (بعد تفعيل بيئة الأدوات):

```sh
. ./bin/activate-hermit
cargo test -q --offline -p buzz-core -p buzz-agent
cargo test -q --offline -p buzz-agent --test project_task_mcp
cargo test -q --offline -p buzz-acp --lib
cargo test -q --offline --manifest-path desktop/src-tauri/Cargo.toml --no-default-features --lib -- project_ channel_workspaces readiness dispatch enforcement handoff review checker
cargo clippy -q --offline -p buzz-core -p buzz-agent -p buzz-acp --all-targets -- -D warnings
cargo clippy -q --offline --manifest-path desktop/src-tauri/Cargo.toml --no-default-features --lib -- -D clippy::all
cd desktop && pnpm typecheck && pnpm check && pnpm test
pnpm build:e2e && PLAYWRIGHT_BROWSERS_PATH=/private/tmp/buzz-channel-workspace-browsers pnpm exec playwright test --config=playwright.channel-workspace.config.ts
```

اختبارات الواجهة تستخدم جسر أوامر اصطناعياً؛ ليست إثباتاً لتشغيل حي. اختبارات بوابة الأذونات تشغّل عملية ACP اصطناعية حقيقية فوق قاعدة بيانات SQLite حقيقية بالجداول نفسها، واختبار خادم المهام يشغّل الملف التنفيذي الحقيقي
`buzz-agent --project-task-mcp`
عبر stdio. لم يُجرَ اختبار مزوّد حي أو حساب حي في هذه النسخة.

## الحدود المتبقية

- القراءة على Claude Code والأوامر داخل صندوق Codex غير مقيدة بقائمة؛ تُعرض هذه الحقيقة في الجاهزية ولا تُخفى.
- الوكلاء غير الأعضاء في الفريق لا يقيّدهم المشروع (سلوك Buzz الأصلي).
- نتائج الفحوص هي ما يبلّغه المنفّذ كمخرجات من نوع
  `check`
  وما يكتبه المراجع؛ Buzz لا يلتقط مخرجات الأوامر.
- الدمج والنشر لا يقوم بهما Buzz؛ يُعرضان كحالتين "لم تُنفَّذ".
- لم يُختبر مزوّد حي ولا التطبيق المثبت؛ التحقق التشغيلي يجري على بناء تطويري معزول بمستودعات اصطناعية فقط.
